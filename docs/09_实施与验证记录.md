## 数据来源与转换

官方 FAST-LIVO2 Google Drive 原始包出现下载限额，首轮使用 [DeepRoboticsLab 公开链接](https://github.com/DeepRoboticsLab/fast-livo2-deep-robotics#3-run-fast-livo2-through-ros2-bag) 的 ROS2 Retail_Street 副本。原包未取得，因此不宣称已验证它与原始 ROS1 文件的 checksum 一致。

对副本的30,157条消息做 CDR→ROS1→CDR 往返检查，全部字节一致；重建 ROS1 输入只将 Livox 类型命名空间映射到官方接口。包含32,520,000个点，图像profile为640×512 RGB8。保留原时间：此数据的 bag记录时间与传感器header时间不同，未擅自统一时间原点。见 `results/retail_conversion_audit.json`。

Hilti 原始包从[发布方数据仓库](https://huggingface.co/datasets/Hilti-Research/hilti-slam-challenge-2022/blob/main/rosbags/exp14_basement_2.bag)下载，SHA256 **18eea013076b8263ababf4f36eb68d331564a0a493262b006dc0dddc2aa85b82** 与官方一致。分别为两版生成相同的 cam0/IMU/Hesai 三话题输入，全部 payload 往返检查通过；ROS2格式不含的 ROS1 Header.seq 是唯一刻意丢弃字段。见 `results/hilti_conversion_audit.json`。

## 已修复的 ROS2 移植问题

1. ImageTransport 收到空节点，且算法内部另建节点；改为共享有效节点。
2. 相机参数依赖 parameter_blackboard，必填参数未声明时被错误置零；改为本节点读取、必填参数声明与校验，覆盖针孔和鱼眼模型。
3. Vikit CMake 导出包含源码路径、主工程硬编码工作区库路径；改为 ament 导出和依赖链接。
4. `lio.max_iterations` 错名、浮点光度参数被改为整数、部分默认值偏离官方；恢复官方语义。
5. Hilti 降采样开关及图像/点云保存参数被声明却未读取；补齐实际读取。
6. `-march=native` 在本机启用 AVX 后，Eigen 分配/释放 ABI 与系统 PCL 不一致，完整回放后发生 SIGSEGV；GDB栈和宏检查确认问题后统一为x86-64/SSE兼容构建，短回放与完整Retail运行均已正常退出。
7. 新增离线启动入口，显式仿真时钟、局部相机配置和实验输出；原 `mapping_aviz.launch.py` 同步更新参数加载方式。

早期失败与中断记录保留在 `results/runs/`，不计入通过统计。`run.json` 中只有 `status=playback_completed` 且 `algorithm_exit_after_signal=0` 的运行才具备纳入条件。

## 2026-09-24 续做记录（环境重启后的补充验证）

| 项目 | 结果与证据 |
|---|---|
| Docker Desktop 冷启动故障 | 残留 socket 占位文件导致 backend 崩溃；把 `%LOCALAPPDATA%\Docker\run` 与 `%LOCALAPPDATA%\docker-secrets-engine` 整目录改名挪开后恢复引擎，不删除任何镜像/容器。一键脚本 `scripts/fix_docker_desktop_stale_sockets.ps1`，细节见 [05](05_Docker_WSL检测.md) |
| 回放覆盖率门限 | `scripts/run_ros1_bag.py`、`scripts/run_ros2_bag.py` 新增 `trajectory_coverage_fraction ≥ 0.99` 门限：节点落后于回放会判为 `incomplete_coverage`，避免把丢帧轨迹当成正常结果 |
| 视觉敏感性矩阵补全 | ROS2 两项单因素补测完成：`exp07_ros2_paperlidar_restore_normal_retry01_1x`（6点误差 16.10 m）、`exp07_ros2_paperlidar_restore_raycast_retry01_1x`（0.81 m）。两次首次尝试因与其它回放并发、输入被丢帧（847 行 / 64 行）失败，原样保留在排除清单。汇总见 `results/aggregated/ros2_sensitivity_completion.json` |
| 环境冷启动复跑 | `coldstart_ros1_retail_01`（Retail，1351 行，覆盖 99.65%）与 `repro_check_ros2_01`（Exp14，738 行，覆盖 99.57%）完整播放、退出码 0；与上一轮归档轨迹按时间对齐后差异 0.39 cm / 1.35 cm。排队、图冲突、尾部截断的尝试分别保留为 `*_contended`、`*_graph_collision`、`*_tail_truncated` |
| 新增序列 Hilti Exp18 | 带连续 6DoF 真值（覆盖前 86.6 s）的第四个序列；每版各跑两次：ROS1 ATE 24.57/23.38 cm、ROS2 12.38/15.06 cm。**同版本两次运行之间的轨迹差异就有 15.21/15.63 cm，与跨版本差异（14.61–24.14 cm）同量级**，所以该序列只能说明“精度随场景变化明显”，不能据此判定移植差异。两版各自用 evo 复核，并用 ±0.5 s 时移扫描排除时钟错位（`results/comparisons/exp18_ros1_shift_scan.json`、`results/comparisons/exp18_*repeatability/`） |
| LiDAR 参数成因分解 | 论文整组参数发散的单项定位：单独恢复噪声（ROS1 4.02 m / ROS2 2.48 m）、结构（ROS1 仍发散 1380 m / ROS2 19.42 m）、抽样（ROS1 2.32 m / ROS2 1.06 m）都改变行为，但没有单项能达到发布配置的 6.93 cm；两版在“仅放宽结构”上行为不同，说明边际参数下上游与移植版并非逐位等价。见 `evidence/lidar_ablation_summary.md` |
| 独立数值复核 | `scripts/audit_report_claims.py` 不依赖报告生成脚本，独立重算 70 条声明全部一致（`evidence/report_number_audit.json`）。需说明的方法学点：Exp07 纯 LIO 两版差异对关联方法敏感（最近邻 0.45 cm、插值到 ROS1 时刻 0.71 cm）；Exp18 的 ATE 也随运行波动（同一序列两次 ROS2 有效回放为 12.38 与 15.06 cm） |

以上补充验证不改变 [10](10_论文对照与多数据集成果.md) 的方法边界：仍无 D455、Mid-360、PX4 真机数据，仍不能把 6 个稀疏位置点等同于官方 Hilti 评测分数。

## 进入已安装环境

ROS1（PowerShell）：

```powershell
docker exec -it fastlivo2-ros1 /usr/local/bin/fastlivo-entrypoint bash
```

ROS2（PowerShell，然后在 Linux shell 中 source）：

```powershell
wsl -d FASTLIVO-Ubuntu-22.04 -u livo
```

```bash
source /opt/ros/humble/setup.bash
source /home/livo/repro/fastlivo2_ws/install/setup.bash
```

自动验证进行中不要在同一 ROS graph 启动第二个算法或修改运行参数。后续自主运行的完整命令以 `scripts/run_ros1_bag.py` / `run_ros2_bag.py` 和对应 `run.json` 为准。
