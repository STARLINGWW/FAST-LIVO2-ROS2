# 冷启动恢复与并发运行规则（2026-09-24 实测）

本文记录 FAST-LIVO2 复现环境在**关机再启动**后的真实状态、已验证的恢复步骤，以及多作业
并发运行时必须遵守的隔离规则。结论均来自本次机器实测，命令与输出见 `evidence/`、`results/`。
配合 [09 实施与验证记录](09_实施与验证记录.md)、[10 论文对照与多数据集成果](10_论文对照与多数据集成果.md) 使用。

## 1. 冷启动时的真实状态

| 组件 | 冷启动状态 | 处理 |
|---|---|---|
| Docker Desktop | 未运行，`docker version` 报 `npipe:////./pipe/dockerDesktopLinuxEngine` 不存在 | 启动 Docker Desktop，轮询引擎，本次约 4–5 分钟后可用（Server 29.6.1）。若“进程在跑但引擎连不上”，属于残留 socket 占位文件故障，按 [05](05_Docker_WSL检测.md) 用 `scripts/fix_docker_desktop_stale_sockets.ps1` 恢复（只改名挪开、不删文件） |
| 容器 `fastlivo2-ros1` | `Exited (255)`；其 CMD 是交互式 `bash`，引擎重启后会自动退出 | `docker start fastlivo2-ros1` 后再 `docker exec` 验证 |
| 镜像 `fastlivo2:noetic-local` | 保留：ID `sha256:c37e61a5c612…`，约 1.02 GB | 不需要重建 |
| WSL 发行版 `FASTLIVO-Ubuntu-22.04` | `Stopped` | `wsl -d … -u livo` 首次调用即自动启动 |
| 容器内 `/datasets`（约 12 GB 数据） | 存在，但**位于容器可写层，不是挂载卷** | 见 §2.3 的恢复命令；删容器即丢数据 |

ROS1 容器为 `--network none` + 容器内 `roscore`，`/work` 绑定到本项目目录；因此 ROS1 的
ROS graph 天然与外部隔离，外界只能通过 CPU 竞争影响它。

## 2. 已验证的恢复步骤

### 2.1 Docker / ROS1

```powershell
# 1) 启动 Docker Desktop（或确认其已运行），等待引擎就绪
docker version --format '{{.Server.Version}}'      # 反复执行，直到打印版本号
# 2) 启动容器并验证
docker start fastlivo2-ros1
docker exec fastlivo2-ros1 bash -lc 'ls /datasets | head'
# 3) 跑一次离线复现（示例）
docker exec fastlivo2-ros1 /usr/local/bin/fastlivo-entrypoint python3 /work/scripts/run_ros1_bag.py `
  /datasets/hilti_exp14_3topics.bag <run_id> --rate 1 --dataset HILTI22 --image-enabled 1
```

### 2.2 WSL / ROS2

```powershell
wsl -d FASTLIVO-Ubuntu-22.04 -u livo
```

```bash
source /opt/ros/humble/setup.bash
source /home/livo/repro/fastlivo2_ws/install/setup.bash
export ROS_DOMAIN_ID=137 ROS_LOCALHOST_ONLY=1 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
python3 /mnt/d/_AAA_CODE_ALL/Tech_reproduction/FASTLIVO2_reproduction/scripts/run_ros2_bag.py \
  /home/livo/repro/datasets/hilti_exp14_ros2 <run_id> --rate 1 --dataset HILTI22 --image-enabled 1 \
  --output-root /mnt/d/_AAA_CODE_ALL/Tech_reproduction/FASTLIVO2_reproduction/results/runs
```

### 2.3 容器数据重建（若容器被删除）

`/datasets` 内容可由本目录重新拷入，无需重新下载：

```powershell
docker cp data/raw/Retail_Street_from_ros2_mirror.bag fastlivo2-ros1:/datasets/
docker cp data/derived/hilti_exp14_3topics.bag        fastlivo2-ros1:/datasets/
docker cp data/derived/hilti_exp07_3topics.bag        fastlivo2-ros1:/datasets/
```

### 2.4 容器 `docker exec` 卡死（2026-09-24 实测）

现象：`docker exec fastlivo2-ros1 bash -lc 'echo ok'` 长时间无输出，但
`docker top fastlivo2-ros1` 只显示一个空闲 `bash`、`docker stats` 显示 `cpu=0.00%`、
`mem=123MiB / pids=1`，即容器本身健康、没有作业在跑。

处理：`docker restart fastlivo2-ros1`，随后 `docker exec` 立即恢复。重启**不会**丢失
`/datasets` 与 `/opt/fastlivo_ws` 中的内容（本次已实测：重启后三个数据包与工作区均存在）。
不要用删除容器的方式处理该现象，否则会丢 §2.3 所列的容器内数据。

## 3. 并发运行规则（本次新增，原因是实测事故）

1. **每个并发作业使用独立的 `ROS_DOMAIN_ID`。** 历史记录默认 73；本次并发验证改用 137。
2. 同一 domain 内 ROS2 节点名固定为 `laserMapping`，两个作业会互相订阅对方的话题：实测出现
   **15,392 条 `imu time stamp Jumps`**，两个 Hilti 包的 IMU 时间基相差 **3,360,241 s**，
   74 s 的包只产出 6.2 s 轨迹，**而退出码仍为 0**。此类运行必须判为无效。
3. `scripts/run_ros2_bag.py` 已内置互斥检查：启动前若发现其他 `fastlivo_mapping` 或
   `ros2 bag play` 进程，直接以 `status=failed` + `competing_processes` 落盘并退出（已用
   负向测试验证）。ROS1 侧因容器隔离不需要该检查，但同样不应并发跑满 CPU。
4. 多个 agent/作业共享机器时，性能数字（处理耗时、RSS、回放墙钟）只能串行测量。

## 4. 覆盖率门限与排水（本次新增）

- G1 门限：**轨迹时间跨度 ÷ 包时长 ≥ 0.99**，否则不纳入统计。
- 两个 run 脚本现在都会计算 `trajectory_span_seconds` / `trajectory_coverage_fraction`，
  低于门限时以 `status=incomplete_coverage` 结束，不再伪装成 `playback_completed`。
- 旧的固定 8 s 排水会截断尾部：节点落后于 1× 回放时，它按传感器速率（约 10 Hz）而不是按
  CPU 能力消费队列。已改为 `drain_until_stable()`：最多等 120 s，连续 6 s 没有新位姿才结束，
  并把 `drain_seconds` 写入 `run.json`。
- 实测对比（Hilti Exp14 1×，74.01 s 包）：固定排水 8 s → 覆盖率 85.4%；自适应排水
  （实际 44.1 s）→ **99.57%**。
- `scripts/audit_coverage.py` 可对全部历史运行重算覆盖率，输出 `evidence/coverage_audit.json`；
  本次 30 个已计入的运行中，29 个历史发布运行全部通过，唯一违例是新增的竞争/截断试跑。

## 5. 本次冷启动后的复现核验结果

| 检查 | 结果 |
|---|---|
| ROS2 移植补丁可重建性 | `manifests/ros2_fastlivo.patch`、`ros2_vikit.patch` 在 fork 基线（`837b7bbc…`、`4b7abc83…`）的全新克隆上 `git apply --check` 通过 |
| ROS2 接口回归 | 针孔与鱼眼两组启动测试均 `passed`（见 `results/ros2_interface_test*/`） |
| ROS2 干净 1× 运行 | `results/runs/repro_check_ros2_01`：738 行、覆盖 **99.57%**、退出码 0、无时间跳变 |
| ROS1 干净 1× 运行 | `results/runs/repro_check_ros1_01`：738 行、覆盖 **99.57%**、退出码 0；ATE **3.73 cm**（发布值 3.83 cm），与已发布 ROS1 运行轨迹差 **4.7 mm** |
| 精度 | 该运行 ATE RMSE **4.27 cm**；同配置历史运行 3.85 cm，按项目门槛（差值 ≤ max(5%, 2 cm)）一致 |
| 论文参数发散定位 | `evidence/lidar_ablation_summary.md`：三项 LiDAR 单因素实验显示“极小测量噪声 + 较粗地图结构/抽样”的组合是发散主因，任一项放宽即可恢复物理合理轨迹 |
| 重复性 | 与历史 ROS2 运行轨迹差异 RMSE **1.35 cm**（中位 1.04、P95 2.52 cm，736 对位姿） |
| ROS1 上游完整性 | 见 §6 与 `evidence/`：上游快照保持固定提交、算法源码未改动 |

同配置跨版本差异（ROS1↔ROS2，1.34 cm）与本次同版本重复性（1.35 cm）处于同一量级，因此
“两版一致”只能表述为**差异不超出运行间波动**，不能表述为逐帧等价。

## 6. 遗留风险

1. `/datasets` 在容器可写层：删除容器会丢约 12 GB 数据，需按 §2.3 从本目录恢复。
2. 1× 实时裕度在多作业并发时明显退化（本次落后约 44 s）；离线结果不受影响，但实时性结论
   必须在独占机器上重新采集。
3. 并发作业的 ROS2 运行必须核对 `run.json` 中的 `ros_domain_id` 与 `competing_processes`，
   不能只看退出码。
